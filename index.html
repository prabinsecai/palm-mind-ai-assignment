Project overview

The backend exposes two REST APIs. The first accepts a document, extracts its text, splits it into chunks with a strategy the caller chooses, creates embeddings and stores them in Qdrant, while the document’s metadata goes to PostgreSQL.

The second is a chat endpoint. It retrieves the most relevant chunks for a question, builds the prompt itself, and keeps the last messages of each session in Redis so follow-up questions such as “And what does it use for memory?” make sense. The same endpoint recognises when a user wants an interview, collects name, email, date and time over several messages, and saves the booking.

Problem

The hiring task asked for a backend with two REST APIs and a fixed set of rules. The rules are what make it more than a standard chatbot demo.

  • Upload .pdf or .txt files, extract text and offer two selectable chunking strategies.
  • Create embeddings and store them in Pinecone, Qdrant, Weaviate or Milvus, with document metadata in a SQL or NoSQL database.
  • Build the RAG flow by hand instead of using RetrievalQAChain, and keep chat memory in Redis.
  • Handle multi-turn conversations and let the LLM drive interview booking with name, email, date and time, then store the booking.
  • Do not use FAISS or Chroma, do not build a UI, and keep the code modular with proper typing and annotations.

Workflow

Document ingestion

  1. Upload. The client sends a PDF or TXT file and picks fixed or recursive chunking.
  2. Extract text. The file type and size are checked, then the text is read out. An empty document is rejected.
  3. Chunk. Text is split into chunks of 1000 characters with 150 characters of overlap (both configurable).
  4. Embed. Chunks are sent to the embedding model in batches of 64.
  5. Store vectors. Each chunk is written to Qdrant with its document ID, filename, chunk index and text.
  6. Store metadata. The document record is saved in PostgreSQL. If this step fails, the vectors just written are deleted so no orphan chunks remain.

Chat request

  1. Receive message. The request carries a session_id and a message.
  2. Load memory. Conversation history and any open booking draft are read from Redis.
  3. Detect intent. The LLM returns JSON with the booking intent and any name, email, date or time found in the message.

Booking intent, or a draft is open

  1. Validate each field in code: email format, YYYY-MM-DD date that is not in the past, HH:MM time.
  2. Merge valid fields into the Redis draft.
  3. If something is missing or invalid, ask only for those fields.
  4. When all four are valid, save the booking in PostgreSQL and clear the draft.

Question about the documents

  1. Embed the question.
  2. Fetch the top 5 chunks from Qdrant.
  3. Build the context and call the LLM with the history.
  4. Return the answer with the sources used.
  1. Remember the turn. The user message and the reply are appended to the Redis history, which is trimmed to the last 20 messages.

How it works

API 1: Document ingestion

A multipart request with the file and the chunking strategy. The response returns the document ID and how many chunks were created.

curl -X POST http://localhost:8000/api/v1/documents/ingest \
  -F "file=@./test_document.txt" \
  -F "chunking_strategy=recursive"
{
  "document_id": "bb216e06-186f-4976-bf9a-642aa889ca25",
  "filename": "test_document.txt",
  "chunks_created": 1,
  "chunking_strategy": "recursive"
}

API 2: Conversational RAG

A JSON request. Reuse the same session_id to continue a conversation.

curl -X POST http://localhost:8000/api/v1/chat \
  -H "Content-Type: application/json" \
  -d '{"session_id": "t1", "message": "What does Palm Mind AI develop?"}'
{
  "session_id": "t1",
  "answer": "Palm Mind AI develops AI-powered applications.",
  "sources": [
    {
      "document_id": "e26b56ed-db14-4637-9dd1-e704f60f5629",
      "filename": "test_document.txt",
      "chunk_index": 0,
      "score": 0.7578998
    }
  ],
  "booking": null,
  "booking_id": null
}

The sources list has one entry for each retrieved chunk. For a booking turn, booking and booking_id are filled in once the booking is saved.

Chunking strategies

StrategyBehaviour
fixedCuts the text into equal windows of the configured size with overlap. Simple and predictable, but can split in the middle of a sentence.
recursiveLooks for a paragraph break near the end of each window and cuts there, so chunks tend to end at natural boundaries. If no break is found it falls back to a fixed cut.

Booking rules

  • The LLM only extracts values. Validation and the final write happen in code, so a wrong guess from the model cannot create a bad record.
  • Relative dates such as “next Monday” are resolved using today’s date and saved as YYYY-MM-DD.
  • Past dates and malformed emails are rejected and asked for again. Missing values are never invented.
  • Details can arrive across several messages because the draft lives in Redis and expires with the session.
  • Booking the same email, date and time twice returns the existing booking instead of creating a duplicate.

Lessons

What worked

  • Letting the LLM extract and the code validate keeps bad data out of the database, even when the model guesses wrong.
  • Keeping the booking draft in Redis makes multi-turn booking natural: users can give details in any order.
  • Writing vectors first and removing them if the PostgreSQL write fails avoids orphan chunks.
  • Separating routes, services, repositories and adapters made the services easy to test with fakes. 16 tests run without any live service.

Known limits and next steps

  • Uploading the same file twice stores its chunks twice, and search returns both. The screenshots show this as two sources with the same score. A content hash check would prevent it.
  • The recursive strategy splits on paragraph breaks only. A sentence-level fallback would improve it for text without blank lines.
  • Chat history is read and then written back, so two simultaneous requests in one session could overwrite each other. An atomic Redis list would fix this.
  • Booking date and time are stored as text. Native date and time columns would be tidier.
  • Authentication and rate limiting are not included.
